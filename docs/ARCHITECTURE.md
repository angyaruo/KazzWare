# KazzWare 0.4.0 architecture

## Runtime and dependencies

The baseline is Lumiverse main `3d74148383dded2b379f204532cf375b52bcd201`, version 1.2.5, with `lumiverse-spindle-types` 0.6.49. Staging-only APIs are not required. Bun 1.4.4 builds two ESM bundles; TypeScript 5.9.3 checks the SDK contract. Bun's test runner and jsdom 26.1.0 exercise backend operations and frontend DOM handlers. `@types/bun` 1.3.11 and `@types/jsdom` 21.1.7 are development types only. The npm lockfile contains the complete transitive toolchain; no npm dependency is imported by the deployed extension.

`shared.ts` defines the versioned wire protocol, persistence types, validation, exact source-range replacement and literal slop matching. `service.ts` contains the backend service and the bounded assistant tool loop. `frontend.ts` owns host UI handles, state subscriptions, correlation IDs and teardown. `message-targeting.ts` chooses a mounted message using the host DOM facade and its visible geometry. `gallery.ts` escapes all model/user strings and produces the complete iframe document. `style.ts` scopes presentation inside extension-owned shadow roots. A removable document style loads the bundled font, outlines marked native targets, and makes this panel's two host wrapper divs ignore pointer hits. Bundles contain the original art as data URLs; no large images travel through frontend/backend messages.

## Ownership and cancellation

The host-authenticated user ID comes from `onFrontendMessage`, never from the payload. Every request has a random document client ID, chat binding token and request ID. Session routing uses the host frontend-session ID when present; payload matching still rejects responses belonging to a different document or binding. `chats.get(chatId, userId)` validates access before the message facade is used. Every generation explicitly supplies both `userId` and the user-selected `connection_id`.

Changing chats replaces the binding and aborts all old controllers. Responses from the old binding cannot update the UI. Jobs serialize per user/chat, including across tabs, so extension writes and state saves cannot race each other. The last 500 request promises are deduplicated in memory; the last 2000 gallery-trigger message IDs are stored durably. A job times out after 10 minutes. Stop aborts unfinished generations; completed edits and their Undo records remain.

## Immediate edits and Undo

An edit captures the message ID, full source text and active swipe. The backend rereads and compares the source before generation and again before writing. It persists a `prepared` Undo record first, then writes only the message's `content`, then marks the record `applied`. If the final save fails, the prepared record can still restore the message. If the first journal save fails, no message mutation occurs. Undo checks the current text and active swipe against the stored result before restoring the original.

The host message API has no atomic compare-and-swap operation. These rereads protect against ordinary stale edits, but another extension/manual write in the final host read/write interval can still race. This is a documented host limitation, not a transaction guarantee. Redo is not implemented. The Undo journal retains 20 message edits; a lorebook creation is not a message edit and is managed in Lumiverse.

Selection offsets are UTF-16 source offsets. Native highlights are accepted only when their literal text maps uniquely after browser whitespace normalization, with offsets mapped back to the original CRLF/bare-CR source. A repeated or formatting-altered selection is rejected; the user can highlight a smaller plain-text passage in the native message. There is no raw-source editing surface. Replacement is a deterministic prefix + replacement + suffix splice; only the interior is model-generated. Partial surrogate selections are rejected.

The no-plot-advancement rule is a prompt constraint, not a provable semantic guarantee. Empty, oversized, malformed and known-truncated model responses are rejected. De-slop results are scanned again using the saved literal phrases and Unicode-aware boundaries; remaining matches cause rejection. It does not invent an automatic second paid retry.

## Assistant and context

The assistant uses a JSON action protocol rather than assuming the selected provider supports native function calling. It has up to eight tool steps plus a final answer. Search scans the full current chat and returns 20 results per page; history pages expose 20 messages. Reference tools read cards, personas, presets/blocks, lorebooks/entries, databanks/documents, connection labels, current-chat memories and saved Kazz summaries. Message edits and new lorebooks stay in the bound chat. Unknown actions are rejected.

Working context includes a bounded recent-message window, character card, chat persona (or active persona fallback), activated lore and the latest Kazz summary. Reference text is explicitly treated as data rather than instructions. Limits and truncation markers are included in tool results. Connection metadata and credentials are not supplied to the model. Generic known credential fields in reference objects are redacted as defense in depth.

Full-chat summaries roll through 24,000-character chunks, incorporating the previous summary each time. The source is checked again before saving. Summaries support up to 1,000,000 source characters and can take multiple provider calls; they may still omit details because model summarization is lossy. The notebook retains ten summaries. They live in Kazz storage, not Lumiverse's native memory system.

Lorebook creation first summarizes the chat, validates 1–20 entries, creates the book, records its ID, adds entries, and merges the new ID into `chat.metadata.chat_world_book_ids`. Existing metadata and book IDs are preserved. Creation is not atomic: interrupted operations can leave a partially filled or unattached book, visible by ID in the notebook. It is never silently deleted.

## Fandom and UI

Gallery automation is opt-in and only accepts successful `GENERATION_ENDED` events explicitly tagged `normal`, with an existing assistant message ID. Swipes, regenerations, continuations, user messages and quiet Kazz calls do not count. The active frontend must be present. Consumed events are persisted before generation to prevent duplicate billing across clients. Failures consume that interval; Fresh drama is the explicit retry. The last 30 pages are retained; each page allows 200 local comments and per-user post likes. Pausing automation preserves saved pages.

Model-generated prose becomes forum, thread or wiki documents through escaped templates. No arbitrary model HTML or scripts execute. The host sandbox has an opaque origin and the manifest requests no CORS proxy or unsafe-eval permission. Its bridge accepts only like/comment payloads whose post IDs belong to the displayed saved page. Pages never invoke agent tools or modify the roleplay.

Two chromeless host widgets hold the mascot and menu. The curled launcher is hidden while the larger composition is open. The menu is uniformly scaled to 0.8 with matching host dimensions and stays floating on mobile. It uses native touch-scroll mode. A dedicated pointer controller moves the mascot, menu title or large artwork through the public moveTo/getPosition API. It disables browser image dragging, accounts for rendered host scale, owns pointer capture, distinguishes taps from drags, and supports arrow keys. Closing, switching chats and teardown cancel gestures. Painted controls accept pointer input, while transparent gaps reach the native chat. Lumiverse's widget and content divs otherwise intercept these hits, so a document `:has()` rule targets only wrappers of the marked Kazz panel. This small compatibility rule depends on the checked host's two-wrapper structure; it changes neither another extension's widget nor the application root. The host clamps mascot movement. Every host handle, document style, observer and event listener is disposed on teardown, and the menu clears old chat content immediately when switching.

Follow view is local to the current chat binding, enabled initially and active only while the menu is open. Captured native scroll events, viewport resize and mounted-DOM changes debounce for 220 ms. `dom.listMessageElements()` supplies IDs and elements without reading private host selectors. The reading line is 48% down the visual viewport intersected with the message's clipping ancestors; messages outside that visible area, detached nodes and zero-size elements are ignored. The nearest message is fetched through the existing authorized backend. Following never scrolls, loads older history, or makes model calls. Picking, native highlighting, focusing a direction field, typing an edit direction, and running an edit pin the target. Resuming follow explicitly clears the old direction and range. Busy operations prevent target changes; binding and sequence checks suppress late selection responses. A separate token prevents an old response from clearing a newer follow request's pending marker.

Pick from chat hides the top, navigation and body while retaining a cancel strip. A capturing document click handler uses `dom.getMessageId()` to identify the native message and consumes that one click, including native message-action clicks. Escape/cancel, chat changes, closing and teardown exit picking. `dom.findMessageElement()` supplies the temporary outline target. The registered Send to Kazz action remains available; the message dropdown and source textarea have been removed. No selection preference or new data schema is persisted.

The native selection prompt is a separate extension-owned shadow root positioned by the selected DOM range and clamped to the visual viewport. It never steals focus while the user highlights. Selection endpoints must resolve to the same native message through public DOM helpers; controls, headings and Kazz-owned injections are excluded. The full stored message is fetched with a binding/sequence guard. Only a unique literal match (or whitespace-normalized match with original UTF-16 offsets) enables editing. Repeated phrases and selections spanning stripped Markdown/HTML are rejected rather than guessed. The prompt keeps the original message/swipe and exact range while its input receives focus. Backend conflict guards and replaceRange still preserve all source outside that range. More options transfers the snapshot into Editor; successful quick edits expose the new Undo record. An explicit whole-message button is the only way to widen a transferred highlight.

Inline Gallery entries use dom.inject(messageElement, '', 'beforeend'), an owned shadow root and the existing host sandbox. The host preserves injection identity across virtualization, including event listeners. A map keyed by saved page ID prevents duplicate entries; a mounted-DOM sweep attaches previously unseen messages, even with the menu closed. Expanding fetches the full page lazily; closing destroys the frame. Each callback checks entry identity and request sequence. Disabling Gallery, switching chats, eviction from the 30-page archive and teardown call dom.uninject to retire replay records. The generation event's message ID pins both context cutoff and page attachment before the model call; a newer reply cannot steal the attachment. The manual generate action snapshots the latest message at start. Future summaries and previous fandom pages are excluded from the cutoff context.

Routine UI replies carry message previews, Undo metadata and gallery page metadata; full sources/pages are loaded individually to avoid the 4 MB WebSocket cap. The visible Kazz transcript shows the latest 50 turns with long-turn excerpts; storage retains 100 turns. Every chat starts with its own settings and a gallery-off default.

## Permissions

`generation` selects and calls saved connections; `chats` reads chat identity and attaches new lorebooks; `chat_mutation` reads/edits messages; `ui_panels` provides widgets/actions. `characters`, `personas`, `presets`, `world_books`, `databanks`, and `memories` support reference tools, with `world_books` also creating lorebooks. Spindle user storage is a free capability. The extension does not request interception, external network, native filesystem/process, secret storage, unrestricted regex, app manipulation or arbitrary code-execution capabilities.
